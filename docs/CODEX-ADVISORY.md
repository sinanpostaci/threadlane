# Read-Only Codex CLI Advisory Workers (`CODEX-ADVISORY`)

This document specifies the support matrix, launch and security boundaries, evidence provenance, and configuration requirements for read-only headless `ToolAdapter::CodexCli` (`WorkerProvider::CodexCli`) advisory worker execution.

## 1. Role and Route Support Matrix

| Workflow Role | Conversational vs. Headless | `ToolAdapter::CodexCli` Support | Route & Normalization Boundary |
| --- | --- | --- | --- |
| `Follower` (Native Coworker) | Human-selected native Codex conversation only (`COWORKER_IS_CONVERSATIONAL_INTERFACE_ONLY = true`) | **Never headless** (no model profile slot or lock; never dispatched as a worker) | Always rejected by `is_read_only_advisory_worker_role`, `normalize_read_only_advisory_choice`, and `validate_non_native_worker_choice`. |
| `Orchestrator` | Read-only planning worker (`CoworkerPlanningService`) | **Supported (read-only advisory)** | Generic `RoleExecutionRoute::from_adapter(CodexCli)` is `NativeHandoff`; explicit `normalize_read_only_advisory_choice` after exact `RegistrySnapshot` + `ExecutionPolicy` preflight normalizes to `HeadlessWorker`. |
| `Architect` | Read-only architectural advice worker (`CoworkerPlanningService`) | **Supported (read-only advisory)** | Same explicit post-preflight normalization to `HeadlessWorker` under an active `PlanningAdviceGrant`. |
| `Reviewer` | Read-only task candidate review worker | **Supported (read-only advisory)** | Same explicit post-preflight normalization to `HeadlessWorker` when authorized by `ExecutionPolicy` and `FrozenApprovalLinkage::authorizes_reviewer_dispatch` (via the frozen `FrozenControllerCapabilityEnvelope`). |
| `Closure` | Read-only combined-candidate package closure worker | **Supported (read-only advisory)** | Same explicit post-preflight normalization to `HeadlessWorker` when authorized by `ExecutionPolicy`, `FrozenApprovalLinkage::authorizes_closure_dispatch` (via the frozen `FrozenControllerCapabilityEnvelope`), and a single-closure `PackageClosureReservation`. |
| `Coder` | Mutating task implementation worker | **Unsupported for headless `CodexCli`** | Rejected by `is_read_only_advisory_worker_role`, `normalize_read_only_advisory_choice`, `validate_non_native_worker_choice`, and `WorkerSpec`. |

- **Generic and manual paths unchanged**: `RoleExecutionRoute::from_adapter(ToolAdapter::CodexCli)` and manual role-flow handoffs (`RoleFlowStore::create_cycle` / `handoff_role`) remain `RoleExecutionRoute::NativeHandoff` and never dispatch a headless worker.

## 2. Configuration and Authority Gates

Saved profiles and registry catalogs never grant execution authority on their own. Running a read-only `CodexCli` advisory worker requires:

1. **Enabled registry tool**: A `ToolDefinition` with `adapter: ToolAdapter::CodexCli` and `enabled: true` in the frozen `RegistrySnapshot`. `resolve_advisory_tool_executable` resolves symlinks and validates the canonical executable from a configured path or resolves `"codex"` (or a bare binary name) from `PATH`.
2. **Exact model and explicit reasoning effort**: A `ModelDefinition` (`model_arg`) and a `RoleAssignment` with an explicit `effort: Some(...)` supported by the model. `resolve_model_target(WorkerProvider::CodexCli, ...)` and `normalize_read_only_advisory_choice` reject `effort: None`.
3. **Explicit `ExecutionPolicy` allow rule**: A `PolicyAllowRule` matching `(tool_id, model_id, effort)` and permitting the target read-only role.
4. **Unchanged workflow authority envelopes**:
   - `Orchestrator` and `Architect` require an active, operator-attested, non-expired `PlanningAdviceGrant` with remaining call budget (`docs/COWORKER-PLANNING.md`).
   - `Reviewer` and `Closure` require a bound `FrozenApprovalLinkage` with an explicit `FrozenControllerCapabilityEnvelope` (`FrozenApprovalLinkage::authorizes_reviewer_dispatch` / `FrozenApprovalLinkage::authorizes_closure_dispatch`) and, for `Closure`, a matching `PackageClosureReservation` (`docs/COWORKER-WORKFLOW-CONTRACT.md`, `docs/PROFILE-FLOW.md`).

## 3. Launch and Security Boundaries

Read-only `CodexCli` invocations use `AdvisoryWorkerSpec` (`provider: WorkerProvider::CodexCli`, `file_permissions: WorkerFilePermissions::ReadOnly`, empty `allowed_write_paths: []`, `standalone: false`, `session_id: None`). `AdvisoryWorkerSpec::validate` constructs the base read-only vector, and supervised structured execution (`run_advisory_worker_with_structured_result*`) splices an invocation-owned `--output-last-message <private_capture_dir>/last-message.json` flag pair immediately before `-- <prompt>`, enforcing the exact pinned argument vector (`is_pinned_codex_read_only_argv` / `extract_pinned_codex_read_only_output_last_message_path`):

```text
codex --no-daemon exec --json --ephemeral --ignore-user-config \
  --model <cli_model_arg> \
  -c model_reasoning_effort="<effort>" \
  -c approval_policy="never" \
  -c model_provider="openai" \
  -c default_permissions="threadlane-advisory" \
  -c 'permissions.threadlane-advisory={"filesystem"={"glob_scan_max_depth"=64,":minimal"="read",":workspace_roots"={"."="read","**/.env"="deny","**/.env.*"="deny","**/codex.toml"="deny","**/.codex.toml"="deny","**/.git"="deny","*/**/.git/**"="deny","**/.codex"="deny","*/**/.codex/**"="deny","**/.agents"="deny","*/**/.agents/**"="deny","**/.aws"="deny","*/**/.aws/**"="deny",".git"="deny",".codex"="deny",".agents"="deny",".aws"="deny"},"/nix/store"="read"},"network"={"enabled"=false}}' \
  -c web_search="disabled" \
  --disable hooks --disable plugins --disable apps --disable multi_agent \
  --disable browser_use --disable computer_use --disable in_app_browser \
  --disable image_generation --disable memories --disable skill_search \
  --disable skill_mcp_dependency_install --disable shell_snapshot \
  --output-last-message <private_capture_dir>/last-message.json \
  -- <prompt>
```

- **Zero model write scopes, private host capture, bounded depth/entry preflight, and clean workdir checks**: `allowed_write_paths` must be empty, and the `threadlane-advisory` permission profile remains strictly read-only (`"."="read"`, `network.enabled=false`). The `--output-last-message` file is written by the trusted `codex` CLI host process into a fresh supervisor-owned `0700` temporary directory outside the repository working directory (`CODEX_ADVISORY_LAST_MESSAGE_FILENAME = "last-message.json"`). Privacy comes from that `0700` owner-only parent directory (`expected_uid`); the captured file itself is opened via descriptor-relative `openat` (`O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`) after verifying an owner-created regular file (`st_uid == expected_uid`, `nlink == 1`, owner-readable, non-executable, no special mode bits, and not world-writable, accepting standard CLI `umask` modes such as `0600` or `0644`) with a bounded byte read (`max_response_bytes + 1`). On drop (completion, cancellation, timeout, or error), the supervisor performs identity-verified (`dev`, `ino`, `uid`), descriptor-relative, non-recursive best-effort cleanup that unlinks only the known non-directory `last-message.json` leaf and removes the `0700` capture directory with `AT_REMOVEDIR` when empty; if unexpected extra entries or subdirectories exist (which fail closed as `ConflictingTerminalOutput` / `SpoofedOrToolOutput`), unknown entries and the non-empty `0700` directory are intentionally retained rather than recursively deleted. Because Codex's Linux sandbox glob scanner requires a finite positive `glob_scan_max_depth` (`CODEX_ADVISORY_GLOB_SCAN_MAX_DEPTH = 64`) for recursive `**` deny patterns, the `threadlane-advisory` profile uses a static root/non-root protected-scope partition: exact root `.git`/`.codex`/`.agents`/`.aws` denies plus protected basename globs and non-root descendant globs (`*/**/.git/**`, `*/**/.codex/**`, `*/**/.agents/**`, `*/**/.aws/**`), so deny expansion does not enumerate every root Git object path. This is not a universal argument-cap guarantee; sufficiently large nested protected trees can still exceed a finite OS helper argument limit. `validate_codex_advisory_workdir` requires a canonical non-root directory and performs a fail-closed, unpruned traversal of all directories (including `.git`/`.GIT`, `.aws`, and `.agents`) before provider invocation. It rejects any entry deeper than `CODEX_ADVISORY_MAX_WORKDIR_DEPTH = 62` relative path components (`glob_scan_max_depth - 2`), any working tree exceeding `CODEX_ADVISORY_MAX_WORKDIR_ENTRIES = 32_768` entries, any symbolic link or non-regular/non-directory special file, and any project-local Codex configuration or hook marker (`CODEX_PROJECT_CONFIG_MARKERS`: `.codex`, `codex.toml`, `.codex.toml`) in, under, or above the working directory. Source and snapshot checkouts are verified clean before and after execution, and stream `type: "error"` / `turn.failed` events remain unconditionally fatal without warning relaxation.
- **No second app-server or persistent daemon**: Each invocation runs as an ephemeral (`--no-daemon`, `--ephemeral`, `--ignore-user-config`) child in its own supervised Unix process group (`process_group(0)`). Threadlane never starts a second shared Codex app-server or installs a persistent OS service.

## 4. Stream Framing, Evidence Provenance, and Usage

- **Invocation-owned `--output-last-message` final response contract cross-checked against terminal JSONL framing**: Official [non-interactive mode documentation](https://learn.chatgpt.com/docs/non-interactive-mode) and `codex exec --help` establish that `--json` streams every `item.*` and turn lifecycle event across a turn (not only the final assistant response), `--output-last-message` (`-o`) writes the final assistant message to a designated file, and `exec --json` does not guarantee `phase` metadata on `item.completed` events. Accordingly, `run_advisory_worker_with_structured_result` never assumes `phase` fields and never performs arbitrary last-JSON selection from stdout; instead, inside a single verified `thread.started` -> `turn.started` -> `turn.completed` lifecycle (`AdvisoryResponseSource::CodexAgentMessageTurnCompleted`), it pairs the invocation-owned `--output-last-message` capture with strict stream validation:
  - Every completed `agent_message` item (`up to MAX_CODEX_AGENT_MESSAGES_PER_TURN = 64`) must occur inside the active `thread.started`/`turn.started` frame, carry a unique non-empty `item.id` across the stream, pass tool/non-assistant role spoofing, error, and truncation/delta/partial checks, have non-empty UTF-8 `item.text`, and fit within `AdvisoryResponseBudget::max_response_bytes`.
  - Read-only tool completions (`command_execution`, `mcp_tool_call`, `web_search`, `file_change`) reset pre-tool message candidates so only a post-tool completed `agent_message` can seal the turn; tool output text is never accepted as an advisory response (`SpoofedOrToolOutput`).
  - Intermediate completed `agent_message` items (including commentary, fenced notes, or intermediate JSON objects) do not disqualify the turn when the validated `--output-last-message` file is a complete top-level UTF-8 JSON object within `max_response_bytes`, matches the terminal post-tool completed `agent_message` item byte-for-byte, and matches at most one post-tool completed `agent_message` in the turn (duplicate final items matching `--output-last-message` fail closed with `ConflictingTerminalOutput`).
  - Missing, empty, invalid-UTF-8, oversized, stale, mismatched, symlinked, non-regular (e.g., FIFO/socket), multi-linked, world-writable, special-mode, executable, or extra-entry `--output-last-message` captures fail closed without falling back to stdout JSON selection. Live `validate_verified_response` requires pinned `--output-last-message` provenance in `constructed_argv`, while `validate_persisted_verified_response` preserves read compatibility for historical pre-repair persisted artifacts.
  - Terminal `turn.failed` or `error` events, missing `thread.started` / `turn.completed` framing, multiple turns, conflicting `thread_id` values, duplicate `item.id` values, or non-zero exit/signal outcomes fail closed. Timeout, cancellation, `EffectUnknown` no-auto-replay, and idempotent duplicate recovery invariants are preserved.
- **Requested vs. observed model/effort (no fallback)**: Actual Linux `codex exec --json` JSONL output does not emit runtime model or reasoning-effort telemetry. `requested_model` and `requested_effort` come from the verified exact pinned launch configuration (`--model` and `-c model_reasoning_effort`) and **must never** be presented as or copied into observed telemetry (`observed_model` and `observed_effort` remain `None` unless genuinely emitted by the CLI).
- **Review and closure evidence provenance**: Pinned Codex launch configuration evidence is explicit and separate from runtime-observed stream telemetry; absent observed model/effort remains `None` with no `requested -> observed` fallback, while legacy `Antigravity` and `OpencodeV2` runtime model/effort telemetry gates remain strict.
- **Genuine token usage (`codex_cli` only)**: When `turn.completed` includes genuine token counts (`input_tokens`, `output_tokens`, optional `cached_input_tokens`), they are captured in `StreamTokenUsage` and projected into `ObservationUsage` (`provenance: "worker_stream"`). Dollar costs, estimates, and synthetic zero usage are never fabricated, and `Antigravity` / `OpencodeV2` usage remains `None`.
- **Independent Activity requester metadata**: Paired MCP requester `selected_model` and `selected_effort` on `ObservationActor` come from bounded once-per-call metadata-only `thread/read` (`includeTurns: false`) over the existing verified managed parent WebSocket endpoint (clearing to `None` on any refresh error or mismatch, with `actor.model` / `actor.effort` remaining `None` and `native_per_call_identity_verified == false`), independent of headless worker execution telemetry. See [`docs/COWORKER-MODEL-OBSERVATION.md`](COWORKER-MODEL-OBSERVATION.md) and [`docs/COWORKER-OBSERVATION.md`](COWORKER-OBSERVATION.md).

## 5. Verification and Platform Qualifications

- **Linux-tested / non-Linux qualifications**: Process-group supervision, `0700`/`0600` private runtime-store gates, `0700` directory-isolated descriptor-relative (`O_NOFOLLOW | O_NONBLOCK`) `--output-last-message` verification (accepting owner-created non-executable, non-world-writable regular files such as `0600` or `umask`-derived `0644` inside the `0700` capture directory) and non-recursive best-effort known-leaf/empty-directory cleanup, and `codex_cli` advisory validation are tested on Linux, and no macOS or Windows acceptance is claimed; the managed native pairing route is Linux-gated and other platform paths must be separately validated.
- **Protocol framing and live acceptance**: Earlier real planning commands failed with `ConflictingTerminalOutput` (`Codex turn emitted multiple completed agent_message items`) before `--output-last-message` was wired, leaving persisted failure reports with no `verified_response` (which are never relabeled or recovered). Retained diagnostics establish that multi-`agent_message` framing failure signature rather than the complete raw stream or full semantic text of every message. Deterministic fake-CLI tests cover intermediate completed `agent_message` items paired with invocation-owned `--output-last-message` capture alongside missing, stale, mismatched, duplicate, oversized, and unsafe capture rejections; installed desktop and live end-to-end provider acceptance remain untested in automated fake-CLI suites.
