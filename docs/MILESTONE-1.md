# Milestone 1: a real, bounded conversation loop

## Scope

Build a small working Rust foundation. Use a deterministic demo worker for this
milestone, not a paid coding agent. No Tauri UI, Git integration, real OpenCode/AGY
adapter or Jev request belongs in this package. Those are later milestone work.

Suggested layout: `crates/threadlane-core` for types/SQLite/state transitions,
`crates/threadlane` for the binary, supervisor, local client, MCP and Codex bridge;
`tests`/per-crate tests for behavioural scenarios. Keep the layout small.

## Required behaviour

1. A separately running supervisor owns the SQLite connection and state changes.
   A process-lifetime lock prevents duplicate owners of a state directory. Use
   short transactions and a schema version. The CLI and MCP connect to that core;
   they do not independently mutate SQLite.
2. Local IPC binds only 127.0.0.1 and requires a freshly generated strong bearer
   secret held in a user-private runtime descriptor. No unauthenticated state
   methods, shell command interpolation or arbitrary executable tool. Protect
   state/descriptor permissions and reject unsafe symlinks. A stdio MCP frontend
   is a thin client. Use the official `rmcp` SDK and supported version negotiation.
3. Native chat binding is explicit trusted CLI configuration, not an MCP call
   that lets an LLM choose any chat. Accept a validated UUID and display label,
   return a software-generated binding ID, and scope each MCP instance to one
   configured binding. No private Codex database access. All run/event/question
   access is checked against the configured binding. Automatic discovery is later.
4. A demo run emits start/progress, waits for a question, accepts an answer and
   finishes after a short bounded delay. Persist its progression so a supervisor
   restart does not lose or repeat its logical effects. This is a deterministic
   simulation; do not claim it proves real external-process recovery.
5. A task has a revision. `steer` with the expected current revision updates its
   instruction, advances the revision, supersedes old pending questions and
   preserves history. A stale answer/steer is rejected. Cancellation is terminal
   for the demo. Completing a cancelled or superseded step is forbidden.
6. Stable caller command keys are scoped to a binding and operation. Identical
   retries return the original result, including after restart. Reusing a key
   for different content is an error. State changes, events and the deduplication
   record commit atomically. Object IDs are generated by software, never parsed
   from an agent's output.
7. Ordered durable events support bounded reads, opaque server-generated batch
   IDs and explicit acknowledgement. Validate binding and delivered high-water
   mark; callers cannot acknowledge unseen/future/cross-binding events. Distinguish
   receipt from processing. Old/repeated acknowledgements are harmless and never
   move the cursor backwards. Event payload sizes and batch sizes are bounded.
8. At most one outstanding wake-up per binding. New important events accumulate.
   Only configured bindings can be notified. A fixed message tells Codex to pull
   events; it contains no instruction/question/worker text or display label.
   The optional bridge calls an explicitly configured Codex executable with an
   argument array: `queue --thread UUID --message FIXED_MESSAGE`. It must not
   override the thread's model, effort, approvals, sandbox or project.
   Persist intent before invocation, enforce a bounded timeout, record submitted,
   failed or unknown. A timeout/crash during submission is not a safe retry.
   Do not automatically replay unknown submissions or produce unbounded wakes.
   Queueing is opt-in for the isolated acceptance test; off by default.
9. MCP tools should cover status/get run, start demo, pull events, acknowledge
   events, answer, steer and cancel. Parameter/schema validation and clear
   structured errors matter. Tool annotations are descriptive, not enforcement.
   Return actionable context while labelling event text as untrusted data.
   Keep protocol output on stdout and diagnostic logs on stderr.
10. Provide a CLI for starting the supervisor, creating a binding, inspecting
    state and running the demo loop without an LLM. Include a self-contained
    smoke script/client. No secrets or raw private chat logs in tracked files.

## Validation and limits

- Formatting, compilation, Clippy and behavioural tests are required.
- Test real stdio MCP initialize/list/call, authentication rejection, two-binding
  isolation, duplicate commands after restart, stale revisions/questions,
  cancellation, event acknowledgement boundaries and recovery of pending wakes.
- A fake Codex executable should prove exact fixed arguments, no model overrides,
  timeout/unknown handling and no repeated dispatch without a valid acknowledgement.
- Race two supervisor starts and show only one owns the state directory.
- After local checks, the primary agent will exercise the existing disposable
  Codex chat. Do not send messages or alter Codex configuration yourself.
- Use Rust crates with pinned Cargo.lock; `rusqlite` bundled SQLite is reasonable
  for portability, `tokio`, `axum`, `reqwest` without unused TLS features, `clap`,
  `serde`, `rmcp` as needed. Avoid hand-building a partial MCP protocol.
- Add a reproducible Nix development shell. Do not update `/etc/nixos`.
- State Linux-only permission enforcement honestly if portable descriptor ACLs
  are not implemented. Cross-platform compilation alone is not platform proof.

## Implementation handoff

Argon High implements the package; the primary agent reviews and runs commands.
If headless tool permissions deny command execution, stop attempting commands
and use file-reading/writing tools. Report the exact missing check; do not claim
tests ran. Do not spawn agents, change models, commit, push, edit outside this
repository, or install/configure global MCP servers. Read official SDK docs as
needed. Keep unsupported behaviours explicit and avoid unrelated enhancements.
